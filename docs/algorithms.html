Algorithm 1 KNN — Nearby Venues

Purpose: Given a user-selected map location, find the K closest active venues within a specified radius using the Haversine distance formula. Returns venues sorted by distance (nearest first).

Concept & Formula

K-Nearest Neighbours (KNN) in this context is a distance-based search, not a classifier. For each venue in the database that has GPS coordinates, we calculate its great-circle distance from the user's pinned location on the map. Venues are then ranked by distance and filtered to only those within the user's chosen radius.

We use the Haversine formula to compute the shortest distance between two points on the Earth's surface:

a = sin²(Δlat/2) + cos(lat₁) × cos(lat₂) × sin²(Δlon/2)
distance = 2 × R × arcsin(√a)

where R = 6371 km (Earth's mean radius)

Why Haversine and not Euclidean distance? Euclidean (straight-line) distance on a 2D plane does not account for the curvature of the Earth. For small distances (a few km) the error is small, but Haversine is the correct formula for geographic coordinates (latitude/longitude) and has zero extra dependencies.

Backend Logic — Step by Step

1

Validate inputs

Reject the request if latitude or longitude are missing, non-numeric, or out of range (lat ±90, lon ±180). Parse optional k (1–20, default 5) and radius_km (0.1–50, default 2.0).

2

Fetch candidate venues

Query all active venues that have non-null latitude and longitude: Venue.objects.filter(is_active=True).exclude(latitude=None)

3

Compute Haversine distance for every venue

Iterate over every venue; call haversine_km(user_lat, user_lon, venue.latitude, venue.longitude). Store as a list of (distance, venue) tuples.

4

Sort by distance (nearest first)

Sort the list ascending by distance. This is the KNN ranking step.

5

Apply radius filter

Discard all entries where distance > radius_km. This is the key correctness step — without it, KNN would always return K venues even if the nearest is 200 km away.

6

Take the top K results

Slice within_radius[:k]. Attach venue.distance_km = round(dist, 2) as a Python attribute so the serializer can include it.

7

Serialize and return

Pass through NearbyVenueSerializer which includes name, sport category, city, price, primary image, lat/lon, and computed distance.

Python implementation (core function)

def haversine_km(lat1, lon1, lat2, lon2):
    R = 6371.0                          # Earth radius in km
    phi1, phi2 = math.radians(lat1), math.radians(lat2)
    dphi       = math.radians(lat2 - lat1)
    dlambda    = math.radians(lon2 - lon1)
    a = (math.sin(dphi / 2) ** 2
         + math.cos(phi1) * math.cos(phi2)
         * math.sin(dlambda / 2) ** 2)
    return R * 2 * math.asin(math.sqrt(a))

# Score, filter, slice
scored         = [(haversine_km(user_lat, user_lng, v.latitude, v.longitude), v)
                  for v in venue_list]
scored.sort(key=lambda x: x[0])
within_radius  = [(d, v) for d, v in scored if d <= radius_km]
nearest        = within_radius[:k]

Algorithm 2 Content-Based Filtering — Recommendations

Purpose: Analyse the authenticated user's confirmed booking history to build a preference profile (favourite sport, usual price range, preferred facilities), then score every active venue against that profile. Return the top-N venues sorted by match score descending.

Concept & Weights

Content-Based Filtering recommends items that are similar to what a user has interacted with before. Instead of comparing users to each other (collaborative filtering), it compares the features of venues the user has booked to the features of all available venues.

Each venue is scored on three dimensions. The final score is a weighted sum:

final_score = (0.50 × sport_score) + (0.30 × price_score) + (0.20 × facility_score)
50%
Sport Match
How often you've booked this sport relative to all your bookings
30%
Price Match
How close the venue price is to your average spend per booking
20%
Facility Match
Overlap between venue facilities and facilities from your past bookings

Scoring Components

1. Sport Score (50%)

sport_score = bookings_for_this_sport / total_confirmed_bookings

Example: user has 3 Futsal bookings and 1 Cricket booking (4 total). A Futsal venue scores 3/4 = 0.75. A Cricket venue scores 1/4 = 0.25. A Tennis venue scores 0/4 = 0.00.

2. Price Score (30%)

diff = |venue_price − user_avg_price| / user_avg_price

if diff ≤ 0.20 → price_score = 1.0 (within 20% = perfect match)
if diff ≤ 0.50 → price_score = 0.5 (within 50% = partial match)
if diff > 0.50 → price_score = 0.0 (too far from usual spend)

Example: user's average spend is Rs 1,000/hr. A venue at Rs 900/hr → diff = 10% → score 1.0. A venue at Rs 600/hr → diff = 40% → score 0.5. A venue at Rs 9,000/hr → diff = 800% → score 0.0.

3. Facility Score (20%)

facility_score = |venue_facilities ∩ user_liked_facilities| / |user_liked_facilities|

The user's liked facilities are the union of all facilities across every venue they've booked. If the user has booked venues with Parking, Changing Room, and Canteen, and the candidate venue has Parking and Canteen, facility_score = 2/3 = 0.67.

Score range: 0.0 (no match at all) to 1.0 (perfect match on all 3 dimensions). Displayed in the UI as 0–100% with colour coding: ≥75% Excellent (green), ≥50% Good (blue), ≥25% Partial (amber), <25% Low (grey).

Cold-Start Fallback

Problem: A new user with zero bookings has no preference profile. The CBF algorithm cannot score venues because there is no history to compare against.

Solution — Popularity Ranking: When a user has no confirmed bookings, the algorithm falls back to counting how many confirmed bookings each venue has received platform-wide, then normalises those counts to a 0–1 score.

cold_score = bookings_for_this_venue / max_bookings_any_venue

Venues with the most confirmed bookings from all users appear first. The reason shown on the card is "Popular with other users". Once the user makes their first confirmed booking, the personalised CBF algorithm activates automatically on the next page load.

Backend Logic — Step by Step

1

Parse N parameter

Read ?n= from query params (default 6, max 20). This is how many venues to return.

2

Fetch user's confirmed bookings

Query Booking.objects.filter(user=request.user).exclude(status=CANCELLED) with related venue, sport category, and facilities. These are the bookings used to build the preference profile.

3

Cold-start check

If booking_list is empty → call _cold_start() which ranks by platform-wide booking popularity and returns early.

4

Build user preference profile

Iterate bookings to build:
• sport_counts — dict of {sport_id: count}
• prices — list of venue price_per_hour floats
• user_facility_ids — set of all facility IDs across booked venues
• booked_venue_ids — set of venue IDs (for "Booked before" badge)

Compute avg_price = mean(prices) and total_bookings = sum(sport_counts.values()).

5

Score every active venue

For each venue, call _sport_score(), _price_score(), _facility_score(). Compute the weighted sum. Store as venue.rec_score. Also set venue.rec_reason (human-readable explanation) and venue.is_previously_booked.

6

Sort by score → take top N

scored.sort(key=lambda x: (-x[0], x[1])) — descending by score, alphabetical as a tiebreaker. Slice to [:n].

7

Serialize and return with metadata

Pass through RecommendedVenueSerializer. Response includes algorithm metadata (mode, total bookings analysed, top sport, average price) plus the ranked venue list with score and reason fields.

Python implementation (scoring loop)

def _sport_score(self, venue, sport_counts, total_bookings):
    if not venue.sport_category_id or total_bookings == 0:
        return 0.0
    count = sport_counts.get(venue.sport_category_id, 0)
    return count / total_bookings

def _price_score(self, venue, avg_price):
    if not venue.price_per_hour or avg_price <= 0:
        return 0.0
    diff = abs(float(venue.price_per_hour) - avg_price) / avg_price
    if diff <= 0.20: return 1.0
    if diff <= 0.50: return 0.5
    return 0.0

def _facility_score(self, venue, user_facility_ids):
    if not user_facility_ids: return 0.0
    venue_fids = {f.id for f in venue.facilities.all()}
    if not venue_fids: return 0.0
    return len(venue_fids & user_facility_ids) / len(user_facility_ids)

# Main loop
scored = []
for venue in venue_list:
    final = (SPORT_W * _sport_score(venue, sport_counts, total)
           + PRICE_W * _price_score(venue, avg_price)
           + FACIL_W * _facility_score(venue, user_fac_ids))
    venue.rec_score = round(final, 4)
    venue.rec_reason = _build_reason(venue, sport_counts, avg_price, user_fac_ids)
    venue.is_previously_booked = venue.id in booked_venue_ids
    scored.append((final, venue.name, venue))

scored.sort(key=lambda x: (-x[0], x[1]))
top = [v for _, _, v in scored[:n]]

Frontend Flow — RecommendedVenuesPage

1

Page loads → fetch recommendations

A useEffect watches [n]. On mount (and whenever the user changes the number selector), it calls GET /api/venues/recommended/?n=N with the JWT from auth context. Shows skeleton loading cards while waiting.

2

Parse response metadata

Store mode, totalBookings, topSport, avgPrice in state. These drive the header description ("Personalised from your 3 bookings · Favourite sport: Futsal") and the algorithm explainer panel.

3

Render venue cards in ranked order

The server returns venues already sorted by score. Cards display: rank badge (#1, #2…), name, city, "Booked before" badge, the match score bar with percentage and label, the reason chip explaining why this venue was recommended, sport, address, and price.

4

Match score bar

score × 100 = percentage. Colour thresholds: ≥75% → emerald (Excellent), ≥50% → blue (Good), ≥25% → amber (Partial), <25% → grey (Low).

5

Algorithm explainer panel (collapsible)

Shows weight breakdown (50/30/20) with the user's actual top sport and average price. In cold-start mode, shows a different explanation explaining popularity ranking and encourages the user to make a booking.

Summary Algorithm Comparison

Dimension KNN — Nearby Venues CBF — Recommendations
Input GPS coordinates (lat/lon) User's booking history
Output Venues within radius, sorted by distance Venues sorted by personalised match score
Core maths Haversine great-circle distance Weighted dot-product similarity
Auth required No (AllowAny) Yes (IsAuthenticated / JWT)
Cold-start N/A — works with no history Falls back to popularity ranking
Sort key Distance ascending (nearest first) Weighted score descending (best match first)
Filter Hard radius cutoff (e.g. 2 km) No filter — all active venues are scored
Live update Yes — re-fetches on pin/radius/k change Yes — re-fetches on n change
Page / Route /nearby — NearbyVenuesPage /recommended — RecommendedVenuesPage
API endpoint GET /api/venues/nearby/ GET /api/venues/recommended/
Map integration Yes — Leaflet.js interactive map No — card grid only
External service Nominatim (geocoding, address search) None — fully self-contained

Key insight: The two algorithms are complementary — KNN answers "what is near me right now?" while CBF answers "what matches my taste?" A user can use both: find a nearby venue on the map, then check recommendations to confirm it aligns with their usual preferences.
